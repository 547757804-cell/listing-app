# 17｜开发协作指南

## 基本流程

1. Issue写出故障层级、影响范围、复现数据和验证目标。
2. 使用隔离branch，不修改原始业务数据。
3. 先加合成fixture，再修业务逻辑。
4. 单元/离线回归后做安全扫描。
5. 记录测试级别和外部调用数。
6. 对runtime改动做单独的process identity/health/hold验证。
7. review通过后再更新正式验收环境。

## Issue模板建议

- symptom与用户看到的错误。
- 观察时间、step、request/trace IDs。
- 是否收到HTTP response及status。
- 输入version/hash、prompt/schema/adapter identity。
- lease owner/heartbeat和task revision。
- 真实根因或ROOT_CAUSE_UNVERIFIED。
- 重现方式、最小修复、回归与剩余风险。

不要上传prompt正文、凭据、真实订单/客户资料、Cookies、数据库或未经脱敏运行日志。

## PR验收清单

- 没有真实SKU/商品识别号、秘密或本机路径。
- 不改变固定SOP或将规划能力标为已实现。
- Stage QA失败不会推进下游。
- Recovery使用当前动态identity与CAS。
- partial不伪装正式artifact。
- 外部请求测试有清晰授权和次数边界。
- 至少说明OFFLINE_PASS与REAL_PASS区别。
- 文档链接/Mermaid有效。

## Issue、版本和证据

Issue可引用脱敏request ID前缀、合成fixture ID、version hash前缀。真正的manifest和原始数据留在权限受控环境。无法公开重现时标UNVERIFIED，并提供内部复现路径的抽象描述。
