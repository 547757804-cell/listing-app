# 18｜卡顿、超时与性能瓶颈深度分析

## 结论先行

一条Listing执行数小时，通常不是17个步骤都在计算。工作流包含外部调用、人工/安全等待、runtime恢复、阶段QA及可能重复执行；其中等待与重做会叠加。当前公开快照没有原始历史数据库/全量日志，所以不能计算项目平均总时长、耗时占比或10 SKU吞吐率。下列代码timeout和历史样例必须与统计值分开看。

## 能确认的计时配置与观察

| 项目 | 可验证内容 | 含义 |
|---|---|---|
| Boloo Pane operation | boloo_web_provider.mjs定义默认135000ms | 配置上限，不是实测平均耗时 |
| AI readiness | ai_generation_recovery.mjs默认15000ms | control-plane预算，不等于generation预算 |
| AI generation | 该模块默认30000ms | default client timeout，不等于所有模型端到端耗时 |
| DeepSeek历史样例 | 对话历史报告过一次约18.75s、HTTP 200、content为空 | 单次故障样例，不能代表模型性能分布 |
| Capability Probe样例 | 历史记录约3.054s及4.562s的PASS | 合成探针样例，不等于真实SOP latency |
| 重复生成 | 历史交接报告有相同SOP generation重复调用/空内容 | 存在重复成本；底层trace全集未纳入公开包 |

历史耗时来自匿名化任务记录摘要，并非本仓库内完整原始telemetry。本表不提供推导出的百分比。

## 时间被消耗在哪里

### 1. 正常业务执行

SOP需要逐步建立正式artifact并执行Stage QA。关键步骤具备依赖链，SOP10不能越过SOP09，SOP14不能跳过事实/关键词/分析输入。序列本身带来不可并行的部分。

### 2. Provider生成

输入规模、长上下文、模型推理和structured output都会影响等待时间。历史中曾报告generation timeout、HTTP 200空content、finish_reason=length、Schema长度FAIL。HTTP 200只是HTTP层成功，不是业务结果成功。

### 3. 页面与Boloo自动化

浏览器导航、页面加载、DOM读取、字段提取、值规范化、bridge写回和parent-child mapping是多个阶段。Pane READY或页面肉眼可见只说明部分链路工作。缺少operation级阶段时间时，不能判断瓶颈发生在WebView2、页面网络还是状态写入。

### 4. 网络与外部依赖

无HTTP response的ECONNRESET/TLS/timeout不能按凭据错误处理；收到status后才按HTTP类别判断。旧readiness早于failure barrier时，不能解除新的等待；重复发相同请求会增加时间和成本。

### 5. 人工等待/安全Hold

验证码、手动登录、HOLD和真实业务决策可能形成较长暂停。当前公开快照没有完整的hold-duration统计，无法量化人工等待占总耗时比例。

### 6. Runtime重启和恢复

需要核对进程、端口、锁、dataRoot和build身份。若Supervisor只凭PID/旧lock判断，可能误判实际状态；若health无效后反复重启，增加恢复时间却不解决业务根因。当前历史原始Supervisor event没有发布，具体次数与持续时间未知。

### 7. QA、artifact与数据库

每步都进行Schema、evidence resolve和Stage QA是质量成本，但不能为了速度删除。可优化重复读/重复序列化；必须记录resolver/QA各自耗时。公开包无可比数据库读写benchmark。

## 为什么会拖几个小时

根因机制往往是串联等待和重复工作：一个远端子任务进入长timeout，后续stage保持依赖等待；过时或身份不匹配的probe无法恢复；retry/circuit失效时重复同一业务attempt；恢复后重复调用先前已成功Provider；最后重新执行QA/resolve，或Runtime/HOLD状态不一致。若每个外部等待达到数十到数百秒，且重复多次，再加人工等待与服务重启，累计时间就会远高于单次正常生成。

这说明“步骤看起来多”不一定是主要原因。没有统一execution_id、attempt分层、request阶段耗时和state transition时间，就不能把时间归因到某个环节。

## 统计缺口与埋点方案

每个operation持久化：

- execution_id、sku hash、step、operation key；
- queue_started、dispatch_started、connect、TLS、request_sent、first_byte、response_finished；
- provider parse/schema/Stage QA、artifact write、DB commit；
- retry layer和attempt number；
- HOLD/dependency wait start/end；
- restart start/end及runtime build identity。

报表应计算P50/P90/P99、成功/失败数、每次实际外部请求数、重复请求成本和等待时长；无数据时显示N/A。

## 优化优先级

### P0

1. **单次请求/dispatch可观察性**：统一execution/request/operation trace，记录response_received和分层elapsed。预期可定位根因；风险是日志含敏感信息，必须做字段白名单。
2. **失败后自动重派门禁**：generation/network barrier与Circuit不得被普通health旁路。验收：故障注入后仅有授权次数、成功partial无重复调用。
3. **Runtime身份一致性**：supervisor、health、server都读同一有效策略；身份不匹配时不派发。

### P1

1. **事务性checkpoint**：SOP06 child result、parent mapping、volume library链接一致提交。
2. **页面操作分层计时与恢复**：READY与operation result分开，结果丢失则查evidence/cache再决定是否重做。
3. **按依赖图并行**：只并行无共享状态/副作用的I/O；每SKU仍隔离，不并行有序SOP。

### P2

1. 大型bol_core拆分为状态、SOP orchestrator、runtime policy和持久化模块。
2. 引入跨SOP的共用证据索引，减少重复序列化，但保持SHA与原始layer。
3. 做合成SKU负载测试，测10SKU下SQLite锁、WebView2实例数和Provider并发。

## 风险与依赖

需要真实operation telemetry、明确日志保留策略和可复现的offline fixture。扩并发可能触发账号限流、WebView2 profile争用或SQLite write contention，不能仅凭理论提升并行度。

## 验证状态

本文件使用源代码默认timeout与历史对话中有限的匿名样例；没有原始performance database，故耗时分布、占比、平均Listing总时间和10SKU吞吐均为UNVERIFIED。
