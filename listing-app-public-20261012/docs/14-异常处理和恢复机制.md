# 14｜异常处理和恢复机制

## 错误层级

1. **Transport**：DNS/TLS/connect/reset/timeout，无HTTP响应。
2. **HTTP/API**：已收到status；4xx、429、5xx分支不同。
3. **Provider生成**：HTTP可能成功但content为空、截断、JSON无效或Schema不符。
4. **业务QA**：输出不符合Facts、evidence或固定SOP。
5. **系统执行**：worker崩溃、lease/state不一致、持久化失败。
6. **Runtime**：进程、端口、HOLD、session、dataRoot或marker不一致。

错误分类不能把这些层合并成一个通用ERROR。

## AI generation recovery

Recovery identity至少锁定SKU、step、输入版本hash、prompt合同/hash、provider、effective model、protocol、adapter合同和schema。failure生成barrier和required readiness-after；普通health不解除generation barrier。新鲜、匹配并在TTL内的generation evidence最多授权对应受控恢复。

## Partial cache与Circuit

Provider成功后应立刻保存partial。恢复时校验全部identity；DeepSeek失败不能导致Qwen重新调用。相同identity重复失败后Circuit OPEN，应阻止自动dispatch，除非存在满足合同的新generation recovery evidence。Adapter内retry不等于业务attempt，须分别记录。

## BOL network barrier

第一次真实transport/no-response故障保存dependency_failed_at和required_readiness_after，不自动重发同一业务调用。仅新的readiness checked_at严格晚于barrier且fresh时才具备恢复条件。

## Lease恢复

发现RUNNING+FAILED或worker消失时，先检查heartbeat、owner和进程身份；不能直接新建并发execution。stale lease只能被显式恢复流程收口；audit历史保留。

## 持久化失败与断点

需使provider partial、正式artifact、Stage QA和task revision分开持久化。若artifact写入成功但task更新失败，应通过immutable manifest和CAS完成finalize，不再次调用Provider。若只有partial，没有正式artifact，则不能将SOP标PASS。

## Mermaid

~~~mermaid
flowchart TD
  ERR[调用/执行失败] --> RESP{收到HTTP响应?}
  RESP -->|否| NET[Transport依赖等待+failure barrier]
  RESP -->|是| HTTP{HTTP status}
  HTTP -->|429| RATE[Rate-limit等待/Retry-After]
  HTTP -->|4xx| CLIENT[确定性请求/业务错误]
  HTTP -->|5xx| UP[上游服务等待]
  HTTP -->|2xx| CONTENT{内容/JSON/Schema}
  CONTENT -->|失败| GEN[Generation barrier/circuit]
  CONTENT -->|成功| PARTIAL[持久化Provider partial]
  PARTIAL --> QA[业务Stage QA]
  QA -->|PASS| ART[正式artifact]
  GEN -->|匹配新鲜probe且允许| CONTROL[一次受控恢复]
  GEN -->|否则| OPEN[Circuit/等待]
~~~

## 人工状态

普通业务判断不应随意进入WAITING_CONFIRMATION。仅固定SOP明确要求人工决策或事实无法安全判定时使用人工等待。技术依赖应映射为WAITING_DEPENDENCY，而不是SKU业务ERROR。
