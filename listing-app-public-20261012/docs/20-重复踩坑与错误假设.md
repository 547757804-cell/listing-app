# 20｜重复踩坑与错误假设

本文记录被项目历史反复纠正的工程假设。它不声称每次故障都由同一底层根因触发。

| 错误假设 | 为什么不成立 | 可靠替代判断 |
|---|---|---|
| HTTP 200意味着成功 | 内容可以为空、被截断或Schema无效 | 检查completed、content、parse、Schema和业务QA |
| HTTP error code足以判断网络故障 | 真实HTTP 4xx/5xx表示收到response；transport failure没有status | 先看response_received与http_status |
| Pane/Bridge READY代表搜索完成 | 仅证明连接或组件状态 | 验证具体operation ID、DOM结果、数值和持久化evidence |
| 页面可见就是数据已采集 | 页面可能没read、identity不匹配或refs未保存 | ASIN/product identity +字段状态+DOM refs+immutable evidence |
| 健康探针PASS可以解除generation失败 | 健康请求和真实长生成具有不同能力/身份 | generation evidence需新于failure barrier且identity匹配 |
| HOLD OFF就会继续执行 | HOLD解除与Continue是不同动作；后台resume可能有竞态 | 获取控制锁、关HOLD、禁止自动抢跑，再显式Continue |
| task status=RUNNING意味着有真实worker | 可能存在陈旧状态或失败lease | 查数据库active lease、heartbeat、owner进程和启动时间 |
| PID/Runtime Lock在文件中就是活进程 | PID可能退出或被复用，锁可能陈旧 | 校验OS进程身份、端口owner与health/runtime marker |
| 引用字符串存在就有证据 | pointer可能不存在、layer错或SHA不符 | resolver读取真实artifact/layer/pointer/hash |
| Candidate 数量等于有效竞品池 | duplicate、C和未证明可比候选不合格 | 完成候选评估、去重后计usable pool |
| 市场字段缺失就阻塞existing评价 | 可将确实取不到的字段收口为UNKNOWN/NOT_AVAILABLE | 用现有充分事实完成分类，记录字段不可用 |
| 多一个seed/词可以通过不相关候选补齐数量 | exact语义和产品方向会被破坏 | 基于Facts选择下一正式核心seed，保留exact strings |
| DONE就等于PASS | Executor执行结束不等于artifact/QA通过 | Stage QA PASS和持久化版本才推进 |
| OFFLINE_PASS就是REAL_PASS | mock和真实环境的网络、权限、输入、runtime不同 | 报告明确测试范围和外部请求数 |
| readiness重复查询能修复旧错误 | 重复readiness不会改变配置/网络根因，可能制造更多请求 | 按分层telemetry定位单一失败环节 |
| Provider失败后重跑整个步骤最省事 | 已成功Provider结果会重复收费并可能改变输出 | partial cache按精确identity恢复 |

## 防止“看起来已修复”

修复之后必须确认当前运行进程加载了新代码、读取正确dataRoot、revision未改变、lease状态清楚。代码修改、离线测试、runtime restart、真实E2E分别是不同证据层。
